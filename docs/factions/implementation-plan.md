# 全卡研究与共享机制分批补全方案

这是交给主实施线程的设计输入，不是引擎修改或发布授权记录。审计基线、原始证据和覆盖状态见 [README.md](README.md)；完整机器可读待研队列见 [card-research-index.json](../../rust-game/data/card-research-index.json)。本阶段全部新记录保持 `selectionEnabled=false`，接受状态为 `notAccepted`；原有 29 个有限定义单独标注 `existingLimitedPool`。

## 研究目录怎样转成规则设计

每张候选牌必须先固定产品/印次、正反面和身份，再完整核对原图。不能用文件 ID、同名、`set-id` 或 `set=测试` 单独决定版本。

核验记录至少补齐：印刷名称和卡号、颜色与徽记分开、卡牌大类/子类别、费用及 X、忠诚、领域、永久与临时图标、防御、起始手牌（如适用）、逐项能力的窗口/来源区域/目标/费用/效果/强制性/次数限制，以及印刷例外。若含其他牌名称、生成指示物、双类型或转变面，须关联原始证据；缺图时不拿另一版同名牌代替。

`confirmedMechanismIds` 只表示人工确认该牌涉及该机制，不表示机制已完整设计，也不表示该牌已实现。`candidateMechanismIds` 是对定位文本做关键词检索的研究提示，误报与漏报都可能出现。当前 29 个 catalog ID 有有限手写规则，但原图完整等价尚未验收，故卡级 `engineStatus=partial`、`acceptanceState=existingLimitedPool`。是否已登记和是否完整支持原作牌必须分开；共享机制的 `implemented` 也仅承诺其列出的有限行为。

实施前应新增一份完整、人工核准的卡级规则规格，再把它映射到有限声明式操作。研究索引不应成为规则 DSL；保留原图与人工规格作为上游，生产 `cards.json` 与规则声明作为下游。不能通过批量导入原始文本、为未知操作写空函数或默认 `supported=true` 来开放卡。

## 共享机制的依赖与边界

依赖数据在 `faction-coverage.json.mechanisms[].dependencies`，代表补全设计需要的概念依赖，不是声称现有引擎已有这些依赖。`interactionIds` 表示需解决的 UI 类别，不是已存在的 React 组件名。

建议先完善事件、费用和选择，随后实现生命周期，再开放复杂产品模块：

- **事件、时机、费用与续体**：可选/强制触发、多人同窗顺序、追加费用、展示作为费用、任意目标槽、付款后目标失效、私密/同步选择。为生成、替代和控制变化提供统一稳定点；仍以小组牌验证，避免一次性重写所有行为。
- **数值与简单关键字**：临时图标、限时修正、一般创伤赋予及移除、护盾生成/消耗、声望、威名、袭击、遏制、迟缓、混乱、灵体/伤害防止。声望是对抗结束后比较未横置声望角色数，胜者至多额外放 1 势力；不能按角色数叠加。灵体比较所在地区双方魔法领域图标，不是按卡面领域种类数比较。
- **秘社与构筑**：独立秘社区、额外初始牌、手牌覆盖、同名上限与印刷例外、颜色/领域/类型限制。不把秘社颜色直接当“允许颜色”，例如盛夏王廷只允许绿牌和仙灵牌，不能擅加全部中立；梦魇主母只允许紫牌。先从基础 MSJC01–09 的小子集核验，复杂秘社仍禁用。
- **附属、封印、拥有者/操控者**：实体载体关系、不同载体种类、可见性、进出场、潜伏/现身清理、载体失效、控制返还、双类型选择。封印牌不在场且不能被指定；载体离场/潜伏回拥有者手。必须让同一实体移动与离场后新实体重入区分开，再实现闪烁。
- **多区域能力与牌库**：墓地直接打出、手牌/墓地行动、先兆、传闻、检索与洗牌、底牌入手、回收、转生及终止。不同来源区域不是普通手牌打出入口的别名；替代进入墓地与进入墓地后触发也不是同一事件。
- **生成、时间和形态**：指示物身份、时间标志、毁灭标志、地区分数调整、领袖与唯一、两面/多形态转变。生成指示物和转变面均不能作为额外玩家卡直接组入牌库。
- **隐秘对抗、秘密计划和传闻**：独立隐秘/暴露、同时秘密承诺和展示、失败与终止、计划隐私和推进条件。不能借用普通调查对抗 UI 暴露本不公开的计划/手牌。
- **模块化产品/模式**：鲜血与饮血依赖附属/封印；修格斯依赖核心区、名誉点、失控、命令及任务胜利；序曲遭遇依赖世界牌库与利用/恐怖；星光扩展把势力与隐秘放在非地区上；洛城危机和统治者必须各有专用状态、流程及胜负判定。

以上是设计顺序而非一次实施清单。具体分组在 [acceptance-groups.json](acceptance-groups.json)：每组代表牌均已看原图，但仍须完成卡级规则核准，不能拿组内代表牌作为完整规则范围。

## 每批开放前的验收

每批流程是：原图完整规格 → 共享操作和状态设计 → 规则实现与针对性测试 → 全部合法动作和私密投影 API → 实际 UI 操作 → 独立策略试玩 → 反馈修复 → 回归 → 由主实施负责人决定开放。

用户要求后续每批用 `dot` 做 **2–4 名独立试玩者**的真实 UI 策略试玩。试玩者按人类使用界面的方式组牌、出牌、响应、选目标、操作区域与胜负流程；不能只发 API 指令或预设一个成功状态。须保留各人的策略、复现步骤、结果、发现的问题和修复后的回归证据。至少覆盖该组的核心合法路线、敌方响应/目标失效、私密信息、持久化恢复和跨组组合；可玩机制与客户端可操作性均须通过。

本审计未启动额外代理、未操作 UI 房间、未执行 `dot` 试玩。配置中的门槛是未来主线程验收要求，所有组 `status=planned`、`releaseApproved=false`，不是伪造的通过记录。

## 需先定规则的疑点

| 疑点 | 原始证据 | 暂行处理 |
| --- | --- | --- |
| 非资产 | 间奏说明图“忽略置资产效果”；霸权 P18 / PDF 第 19 页只禁止建立资产，允许其他效果置资产 | 按产品/规则包固定语义，未确认前不开放依赖牌 |
| 来源在响应中横移时的“本地区”锚点 | 勘误及释疑 P4、P5 的案例需一起核对 | 当前只开放 JC014 自机动，不据此推断任意横移组合 |
| 测试/正式印次冲突 | BQ010、BQ105、TEST015 原图与 locator 测试标签或编号不一致 | 保留独立版本疑点，不自动删除或纳入正式可玩池 |
| 缺少原图 | DQBQ01–10、TK004、TK010、TK011 | 不绑定同名另一版，等待同 ID 原图/产品规则 |
| 永恒 | LC15 莲月合一卡图明确有词，已核说明页未找到完整定义 | `uncertain`；不由名称推断持续或不离场语义 |
| 洛城专用机制与一般对战的适用性 | MSLC01–04 的危机、剧情、支援、威胁字样 | 待原模式手册；不把所有洛城卡整体判为可玩或不可玩 |
| 卡号及小册子产品编号 | 例如 BQ010 / BQ105 的原图印刷序号与文件 ID 不同 | 逐张记录印刷代码；不按 locator 编号替代原图身份 |

世界地区 DQJC116 香港还需要“同时展示 → 同时入手 → 再洗牌”的完整流程。当前有限池恰好不含附属，不足以证明其正式规则已支持，也不能移除隔离。

## 主实施线程的集成方式

主线程可 cherry-pick 本分支提交，先用独立覆盖数据做只读浏览与覆盖标注，再按分组实现。不必在 UI 引入完整研究索引；颜色、秘社摘要和牌组概念用较小的 `faction-coverage.json`，研究索引留给开发和审核工具。

将官方颜色导航、秘社列表、基础两色规则说明与当前可选预组分开。导航可浏览白/紫及其他未齐颜色，但不得发出选择未实现派系/秘社/任意两色牌组的开局命令。真正的可选牌组仍以运行时 `/api/catalog.decks` 为准。数据缺失、未知状态或源码快照过期应显示“待复核”并禁用对应新内容。

主线程更新任何被审计文件后，严格验证可能因源码 SHA-256 变化而失败，这是覆盖记录过期的信号；先重审受影响声明和数据，再更新基线/快照/状态。`--allow-code-drift` 仅用于读取漂移警告，不能作为通过发布验收或自动升级状态的方式。
