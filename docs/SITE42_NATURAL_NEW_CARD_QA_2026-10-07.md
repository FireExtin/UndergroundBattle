## 固定种子与合法牌组

生产建桌 API 没有 seed 参数。因此本地 ignored adapter 仅在建桌请求供应固定工厂种子16时截获恰好8字节的 RNG 调用，按原大端格式提供 seed；房间、邀请、认证、nonce 等其他随机调用仍由原 RNG 完成。adapter 直接委托同一编译 Worker，未改手牌、牌序、牌桌、选择或持久化状态，未进入产品提交或发布。源码与配置完整保留在证据中。

在实际正式 WASM 中仅检查32个合法工厂种子并选16；三次实际建桌都用16，没有第四张新桌或无限搜索。两套合法50张牌组没有会社：

| 玩家 | 每种3张 | 其余 |
|---|---|---|
| A | XQ40、XQ41、XQ45、JZ58、JC104、JZ59、JZ61 | JC125 ×29 |
| B | XQ16、JZ50、JZ49、JC085、JC029、XQ12、JZ48 | JC125 ×29 |

浏览器只预置合法牌组库元数据，之后实际点击保存选择、创建、独立玩家会话、邀请码加入、准备、开始与保留起手。后续资产、派遣、暗置、现身、能力、响应让过、阶段让过经正常 HTTP 命令推进；选择、暂停、刷新恢复、阅读和最终暂停在实际 UI 操作。主桌 **19条命令由实际 UI 请求产生，59条由原驱动正常HTTP产生，313条由HTTP sidecar产生**；391个commandId与服务端canonical journal逐项吻合，无缺失、额外请求或席位注释不一致。不能将这些HTTP推进动作表述为全程鼠标对局。

单页最初切换的是 UI 自己生成的独立玩家存储 namespace。云端工具连接刷新后，原驱动 stdin 出现 `OSError: [Errno 5] Input/output error`，finally已保存结果、浏览器结束。后续浏览器从这张本地桌原始UI建桌/加入的两份entry ACK恢复真实原席位认证，凭证只留在内存和浏览器认证存储，未导出。没有伪造令牌或运行时状态。原席位恢复是该后续浏览器驱动的明确边界，不作为第二次独立会话创建测试。

## 失败、预算与未覆盖项

最多3张新桌、每桌400条已提交命令的预算守住。第一次双页桌只到版本4、3命令，出现截图“Unable to capture screenshot”和peer reload `ERR_INSUFFICIENT_RESOURCES`；第二次单页桌只到版本2、1命令，bootstrap出现TargetClosed。两桌没有机制通过声明。第三桌在图像解码关闭的单页浏览器完成上述链条；截图用于文字、选择、归属和状态验证，**不代表原图或美术验收**。此前共享内存约16.1/17.2GB，未证明OOM就是失败根因。

早期自动推进把真实 `deploy` 误写成旧 `play`，响应让过包装也需按真实session类型修正；因此前两回合主要放资产和正常让过，手动合法派遣后继续，不把这类驱动问题记作产品错误。后续阅读检查曾错用空数组可省略字段、触发简称和单图标条预期，离线factory wrapper和归档drizzle路径也曾使用错误比较/映射；修正驱动预期后相应检查通过，原始失败与修正记录保留。
