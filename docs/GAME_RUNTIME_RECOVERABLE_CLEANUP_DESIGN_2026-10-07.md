## First user entry: room recycle bin

Add a small room-management control near the current table/lobby, independent of deck construction: `离开此桌` clears only this browser session; authenticated seat0 gets `移入回收站` with room name/scope, then a visible `恢复牌桌` entry. Other seats cannot delete a room; another room token or invite cannot authorize it. Keep a management credential after recycling so the host can restore. A recycled room stops polling/game input and returns explicit `room_deleted`, while the interface explains that the server data remains recoverable. This first step does **not** claim to save database bytes.

Proposed API is limited to room lifecycle: authenticated management status, archive and restore for one room. Room metadata carries archived_at and a lifecycle revision; a small operation receipt provides stable operationId retry. Existing rule entities and frame queues remain untouched. Management auth uses seat metadata without loading a historic Game, so an unsupported old room can still be recycled. All state/catalog/join/command/quote/system-tick and entry-receipt return paths must check lifecycle before invoking a kernel or returning a seat receipt. Every write transaction includes active/lifecycle guards. Restore invalidates pre-archive requests before reopening; the exact wrapper revision/lifecycle wire contract must be audited before implementation, rather than accepting late old actions by accident.

Preserve all five tables during first-stage recycling, so current replay and receipt semantics remain intact. Restoring a room from an older kernel is data recovery, not automatic compatibility in the upgraded game. Playing that backup requires its matching deployment rollback. No automatic permanent purge/TTL is introduced.

## Upgrade reset: owner operation, not a player button

Use the supported Site owner/database backup facilities after their actual availability and permissions are checked. A seat0 token grants management of one room, not full-database operation. Do not add a public global-clear endpoint. Target is exactly the five application runtime tables plus necessary lifecycle receipts; do not DROP schema/migrations, Site settings, originals, code, or browser-saved decks.

The reviewable operation follows: (1) record exact project/deployment/DB, operationId and readonly row counts; (2) persist maintenance stop and guard every writer, including in-flight create/join/timeouts/retries; (3) make a consistent private backup of all five tables, preserve opaque state/u64 strings verbatim, hash and count it, and prove an isolated restore; (4) transactionally clear children `entry_receipts`, `commands`, `journal`, `seats` before `rooms`, bound to one maintenance generation and one operationId; (5) verify empty runtime tables/no orphans and resume new current-kernel rooms. Retrying the same operation must return its saved result, never clear rooms created after resume.

Backup includes private cards and entry receipts with seat credentials. Store it only in an authorized private operational backup destination; never in GitHub, Site static assets or player downloads. Platform backup tooling, owner operational auth and snapshot consistency are still unverified, so no live reset execution is ready. Restoration again stops writers, handles newly created room conflicts explicitly, restores all related rows/receipts/opaque bytes together, and uses the backup's matching Site deployment where necessary. Backup destruction remains a separate explicitly confirmed action.

## Minimum actual checks for the implementation

Add real local shared-DB two-room tests: same commandId/version accepted separately; A waiting for a private choice does not stop B; foreign-room credentials rejected for state/command/quote/archive/restore; recycling A leaves every B row byte identical; restore and in-flight writes/old receipts cannot cross lifecycle revisions; failed SQL rolls back all tables; reset retry does not delete post-reset new rooms; isolated backup restore matches row counts, raw bytes, foreign keys and actual replay. These are consistency checks, not capacity benchmarks. Measure row/text/file sizes and concurrent request latency separately before reporting any number of supported tables.
