## 实现与客户端契约

- 默认真实 registry 只有 MSJC09，普通卡仍是原来的48张；MSJC01、MSJC16 和全部 FIXTURE 名称不被默认牌组接受。秘社独立于五十张普通牌组，原有四席 `societyZones`、`sourceZoneId`、支付帧、私密投影和持久化结构继续使用。
- 标准、可响应能力 `drawWithInitiative` 支付 `Assets(3)` 与 `ExhaustSource`，新增有限操作 `DrawIfActorHasInitiative`。条件在结算时检查演员队伍；两位先手队友分别可以操作自己的秘社，分别付费并抓自己的牌。队伍共有先手不授予操作队友秘社的权限，也不把能力使用次数变为队伍共享。
- `deckBuildRules.societySupported` 根据实际秘社 registry 是否非空生成，不以编译 feature 代替 registry。基础的无秘社席位仍具有稳定空区。
- 秘社 catalog 新增只读 `subtitle` 和 `printedCost`（MSJC09 为 `null`）；展现用 `CardView.cost` 对秘社省略。旧 `CardDefinition` 的整数 `cost:0` 是内部兼容字段，不能渲染为印刷费用。正文中的行动3是能力支付，不能当作登场费用。
- 默认身份 `rust-v0.2.8-msjc09-candidate`。`society-fixtures` 身份 `rust-v0.2.8-msjc09-fixture`，仍只有原来三张人工 FIXTURE 秘社，不含真实 MSJC09。两者 registry、WASM 和状态身份隔离，交叉恢复拒绝；FIXTURE 的历史 `U13-test-unresolved` 仅是测试占位，不代表 MSJC09 仍未裁定。
- 所有八个冻结内核 v0.2.1–v0.2.8 相对基础提交字节不变。当前普通卡及预设与冻结 v0.2.8 深比较一致。私有默认及 fixture Worker 各有九核：八旧核加对应候选核。

| 默认 Worker 完整入口 | 23通过、0失败、0跳过；新增 MSJC09 场景使用正常 HTTP 房间命令，无初始布局或 D1 状态注入 |
| MSJC09 Worker 场景 | 四席，2346 HTTP 调用、461接受命令；先手／后手都实际支付，两个付费帧均在到期前实际关闭并重开 workerd/D1，保留 opaque 状态、响应成员／窗口、收据、四席隐私；正常下一回合同一 instance 恢复竖置 |

单元测试明确使用人工布局，覆盖声明先手／后手与结算先手／后手的四种组合、错误席位／队友、支付不足、来源已横置、错误时机、非空堆叠、拒绝原子性、一次付费和序列化帧。改变结算 `firstTeam` 是明确的单元测试布置，不声称当前普通牌池已经有自然响应改变先手的卡。

新增 oracle 及 Worker 场景通过正常创建、加入、ready、start、mulligan、资源、发动和 pass 命令构成三回合付费及第四回合重置，没有初始状态注入。它们是本地自动化验证，**不是自然浏览器 UI，也不是公网 Cloudflare D1 验收**。未调用公网房间或任何旧凭据。

开发中两项新测试曾失败：一项手动修改内层 Game 后未同步外层 Room 版本，随后将该手动重置段改为 Game 序列化验证（真实 Room 恢复另有完整测试）；另一项把全场资源当成个人资源计数，修正为按 actor/controller 过滤。没有为消除这两个断言错误而修改运行时规则。复核包保留初次 Worker 失败日志及最终完整通过日志。
